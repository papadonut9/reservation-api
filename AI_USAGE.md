## IMS-32 reserve: atomic seat claim
- Directed by human: IMS-32..35 designed together as one reserve flow; spec body and correctness bar supplied by human; phase-wise plan (test base, DTOs, advice, claim, admission, tests) written and revised by human over several review rounds; human makes every commit from AI-prepared file lists and messages.
- Suggested by AI, approved by human: `SELECT ... ORDER BY seat_no FOR UPDATE NOWAIT` then `UPDATE` (over JPA `findAll`/`saveAll`, which is read-then-write, and over a guarded `UPDATE ... = ANY()`, which can deadlock and cannot tell an unknown seat from a taken one); seat step last in the transaction so the lock holder has nothing left to fail; leasing deferred to IMS-44 since the spec returns `confirmed` immediately.
- Caught by AI in human's plan: dedupe and unknown-seat 404 had to move into IMS-32 or `[A1,Z99]` / `[A1,A1]` would be charged for seats never claimed; pool exhaustion arrives as `CannotCreateTransactionException`, not the bare Hikari type; invariant and hot-seat tests needed one user per request or IMS-34's limit would change their outcome; `finally { release() }` after a timed-out `tryAcquire` mints permits; the pool-exhaustion test could not catch that, so a drained-semaphore test was added.
- Refined by human after checking sources: Hikari 7.0.2 clears its last connection failure on refill but not after a failed validation, so DB-down vs pool-exhausted is decided by an `08` SQLState or a `ConnectException` on the Hikari exception; the stale-state edge case is documented rather than coded around.
- AI decided: 55P03 detected by SQLState in `lockSeats` (Spring's translated type for it is not guaranteed); advice classifies database errors by SQLState anywhere in the cause chain (55P03/57014/40P01 -> 409 `busy`); stackless `ConflictException`/`OverloadedException`; timeouts set with one `set_config(..., true)` query; fair semaphore of `max(1, pool - 2)` permits so readiness and GET keep two connections; `admission-wait` in config, to be tuned from burst numbers.
- Open for human: `request_hash` is stored but not yet read (IMS-33 replay); 429-vs-409 numbers under a 20k burst are measured in the burst ticket.

## IMS-33 reserve: idempotency
- Directed by human: phase 2 of the reserve plan (same key replays, changed body 409, failures not stored); 
- Suggested by human, verified by AI (plan rounds): `INSERT ... ON CONFLICT (user_id, idempotency_key) DO NOTHING` instead of catching the unique violation, which would abort the transaction; a same-key request in flight makes the second wait on the unique index, then replay (commit) or proceed (rollback); `request_hash` as the readable `"show:A1,A2"` string so the replay body is rebuilt from it even after a cancel frees the seats; parallel test asserts 201-or-`busy`, not all-201, since a waiter can outlast `lock_timeout` on a slow runner.
- Human decided: replay happens inside the same transaction right after the no-op insert, before any seat lock (and before the IMS-34 quota step), so a replay moves nothing; `findByKey` runs as a new READ COMMITTED statement so it sees the row that blocked the insert; no-op insert with no stored row means the show is missing → 404; the stored row type is a record nested in `ReservationRepository` (one use, no new file); replay status is always `confirmed` (original body).
- Open for human: replay after cancel returns the original `confirmed` body; confirm when IMS-36: Item cancellation lands.

## IMS-36 cancel
- Directed by human: brainstorm before code; spec lets us choose explicit cancel or an expiring hold.
- Suggested by AI, approved by human: explicit cancel (reserve already confirms, so no hold state, clock or sweeper); lazy expiry rejected because the quota counter and the `seats` gauge would drift; one transaction in reserve's lock order (guarded `UPDATE reservations` → quota decrement → `UPDATE seats WHERE reservation_id`); seat count from the stored `request_hash`, no new column; no admission permit on cancel, pool exhaustion is already 429.
- Human decided: 204 for every successful cancel including a repeat; replay after cancel returns the current status (`cancelled`), overriding IMS-33's "always `confirmed`"; non-owner → 404 per CLAUDE.md (human weighed 403 and kept 404).
- Human decided: a follow-up `EXISTS` read chooses 204 vs 404 only after the guarded UPDATE matched nothing (never decides a write); shared row mapper for `findByKey` and the cancel `RETURNING`; test helpers (`user`, `key`, `seatStatus`, `held`) moved up into `IntegrationTest`; replay and cancel code in one commit since they touch the same files.
- Tests: rebook after cancel, repeat cancel leaves the new owner's seat and quota alone, other user → 404 with nothing moved, unknown id 404 / bad id 400 / no token 401, cancel frees quota at the limit, replay after cancel says `cancelled` and moves nothing.

## IMS-38 zero-5xx hardening
- Directed by human: brainstorm before code. AI's gap analysis found most of the ticket already shipped in IMS-32..35 (advice, semaphore, timeouts), leaving the proof test, the admission sizing and docs.
- Human decided: one table test over the advice is the "no domain path returns 500" proof, plus one row that must stay 500 so a real bug is visible; 429 is an overload valve, not an expected outcome (a 429 on a hot seat breaks "one 201, rest 409"), so the admission wait goes from 2s to 15s; WRITEUP documents the formula `wait ≈ N / tx/s` with N = 1000 expected, 2000 stress and 500 for the hot-seat storm; local tx/s overstates the deployed database, so IMS-42 re-checks the ceiling; Fly `[http_service.concurrency]` belongs to IMS-42.
- Caught by AI in human's plan: validation and auth never reach the advice, so the table test cannot cover them (existing MockMvc tests do); a plain `RuntimeException` row tests Spring, not the advice, so the 500 row is a `BadSqlGrammarException`; drain-time sizing (20k / tx/s) assumed unbounded concurrency, while a capped client keeps the semaphore queue at most N deep.
- Caught by AI while building: a lock or timeout exception without the driver's `SQLException` in its cause chain fell through to 500, so a type backstop was added (`PessimisticLockingFailureException`, `QueryTimeoutException` → 409 `busy`); mutation-checked, with the backstop removed exactly those three rows fail. Human asked for `DeadlockLoserDataAccessException` to log at WARN; it has been deprecated since Spring 6.0.3 and is no longer thrown, so the WARN keys on SQLState 40P01 instead.
- Human verified, AI confirmed: the semaphore is already fair (`new Semaphore(permits, true)`) and the timed `tryAcquire` honours fairness. The env override `APP_RESERVE_ADMISSIONWAIT` works through relaxed binding, no code needed. Tests pin the wait at 2s so the drained-semaphore test does not wait 15s.
- Open for human: the 20k local burst and the measured tx/s need the IMS-41 script; WRITEUP holds them as pending.
